# 检索效果评估（eval）

本目录是本项目**唯一的"效果证据"来源**：所有关于检索质量的数字都在这里可复现。

```text
eval/
├─ eval_retrieval.py          通用评测脚本：可切换向量器与向量库目录，输出逐题明细
├─ eval_ablation.py           消融对照脚本：两种向量器 × 6 种融合策略
└─ results/
   ├─ ablation_对照表.txt              消融主结论（34 道计分题）
   ├─ retrieval_bge_m3_1024d.txt      1024 维 BGE-M3 逐题明细
   └─ retrieval_hash_384d.txt         384 维哈希向量器（降级路径）逐题明细
```

---

## 一、评测集怎么来的

- **34 道计分题**，覆盖全部 6 份源文件：3 份「100问」各 6 题、故障排除 6 题、维护保养 5 题、选购指南 5 题。
- **query 是口语化改写**，刻意**不等于条目标题原文**（例如条目标题是"如何设置定时清扫？"，query 写成"怎么设置每天固定时间自动打扫？"），避免"标题字面命中"把分数虚高。
- **标准答案用「来源文件 + 条目号」锁定**。3 份文件各自独立编号（都从 1 到 100），所以该组合唯一，例如 `扫地机器人100问.pdf#22` ≠ `扫地机器人100问2.txt#22`。
- 另外 4 道**「知识库确实没有答案」**的题（含域外题"洗衣机脱水声音大怎么修"），单独用来考察"无答案时会不会硬答"。
- 指标：**Recall@5**（正确答案是否进前 5）、**MRR**（正确答案排多前）、**平均命中名次**。

---

## 二、怎么复现

```bash
# 1) 先建两套向量库（1024 维正常路径 + 384 维降级路径）
.venv/Scripts/python.exe scripts/build_kb.py                     # 默认 -> ./vectorstore

set VECTOR_BACKEND=local
set CHROMA_PERSIST_DIR=./vectorstore_bge1024
set EMBEDDING_ALLOW_DOWNLOAD=true
.venv/Scripts/python.exe scripts/build_kb.py                     # -> ./vectorstore_bge1024（1024 维）

# 2) 消融主对照（两种向量器 × 6 种策略）
.venv/Scripts/python.exe eval/eval_ablation.py

# 3) 单向量器逐题明细
set EVAL_EMBED=bge
.venv/Scripts/python.exe eval/eval_retrieval.py
```

可用的环境变量：

| 变量 | 作用 | 默认 |
| --- | --- | --- |
| `EVAL_PROJECT` | 项目根目录 | 脚本上一级 |
| `EVAL_PYTHON` | 用哪个解释器跑子进程 | `<项目>/.venv/Scripts/python.exe` |
| `EVAL_STORE_HASH` / `EVAL_STORE_BGE` | 两套向量库目录 | `./vectorstore` / `./vectorstore_bge1024` |
| `EVAL_RESULT_DIR` | 结果输出目录 | `eval/results` |
| `EVAL_EMBED` | `eval_retrieval.py` 用哪种向量器 | `bge` |

> **为什么 `eval_ablation.py` 要开子进程**：项目的 `settings` 是导入期创建的单例，`get_embeddings()` 又带 `lru_cache`，**同一个进程里改环境变量切不动向量器**——不分子进程跑，两次结果会完全一样（这个坑踩过一次）。

## 三、结果（34 道计分题）

| 融合策略 | 384 维哈希（降级路径） | 1024 维 BGE-M3（正常路径） |
| --- | --- | --- |
| A 纯向量 | 0.706 / 0.576 | **0.971 / 0.801** |
| B 纯 BM25 | 0.676 / 0.578 | 0.676 / 0.578 |
| C RRF 融合（k=60） | 0.735 / 0.619 | **0.971 / 0.754** |
| D C + 覆盖度加权（**线上配置**） | 0.735 / 0.619 | **0.853 / 0.728** |
| E C + 覆盖度加权 ×10 系数 | 0.765 / 0.599 | 0.853 / 0.680 |
| F 纯向量 + 覆盖度加权 | 0.706 / 0.627 | 0.941 / 0.729 |

格式为 `Recall@5 / MRR`。BM25 一路与向量器无关，两列数值相同，可作为实验自洽性的交叉验证。

---

## 四、结论（含"哪个优化其实没用"）

1. **换 Embedding 模型是收益最大的单项优化**：384 → 1024 维，命中数 24/34 → 33/34，Recall@5 **0.706 → 0.971**，MRR **0.576 → 0.801**。这是同题、同代码、只换向量器的干净对照。
2. **覆盖度加权在当前系数下没有贡献，且在强向量器下有害**：
   - 384 维下 C 与 D **完全相同**（0.735 / 0.619）——这一步没有产生效果；
   - 1024 维下 C **0.971** → D **0.853**（33 → 29 命中）；
   - 原因：`_rrf_fuse` 的 RRF 分数只有 ~0.03 量级，而加权项最大 0.010 且对比度极高（0 或满值），相当于往已排好的序列里注入噪声。系数放大 10 倍（E 组）在 1024 维下仍是 0.853，说明**不是缩放问题，而是该信号本身无效**。
3. **覆盖度加权唯一起正面作用的地方**：384 维下「纯向量 + 覆盖度」（F 组）把 MRR 从 0.576 提到 **0.627**（平均命中名次 1.54 → 1.38）——它能把**已命中**的结果往前排，但**拉不进新的正确答案**。
4. **已知缺陷（下一步要改）**：`HybridRetriever.retrieve()` **没有最低相关度阈值**，永远返回 top-k。4 道"知识库无答案"题在 4 种配置下**全部返回了内容**，即检索层没有拒答能力，"不知道就说不知道"目前只靠 Prompt 约束兜底。
5. **待办**：接口延迟 / SSE 首字时间尚未实测；评测集可继续扩到 100 题以上提高置信度。

---

## 五、注意

- 两套脚本独立跑出的结果**完全一致**，且反复重跑数值不变（哈希向量器与 BM25 均为确定性算法），因此这些数字可以引用。
- `results/*.txt` 是脚本的原始输出，请勿手改；要更新就重跑脚本。
